## 第 1 章 · 接入前判定:先看产品形态(今天的跟头就在这里)

**任何 harness 接入,第一个问题不是"怎么跑它的 CLI",而是"这个产品的本体是什么"**。三种形态:

| 形态 | 特征 | 执行体选谁 | 凭证策略 | 实例 |
|---|---|---|---|---|
| **CLI-first** | CLI 即产品完个体,登录态落本机(auth.json 类) | 直接用 CLI(`xxx --acp`) | 用户一次性登录 CLI,spawn 即用 | opencode / kimi / zcode / dsh-acp |
| **GUI-first** | GUI 是产品本体,CLI 是 GUI 的"手"(凭证由 GUI 注入 worker) | **GUI 的 Gateway/Daemon**,不是裸 CLI | 复用 GUI 活登录态;**绝不让 CLI 独立登录**(逆产品设计) | **workbuddy**(5.8.2,实测) |
| **daemon-first** | 产品以常驻服务形态存在,CLI 只是客户端 | Daemon 的 HTTP/RPC 接口 | 服务的鉴权(token/密码) | (待遇实例) |

**判定清单(5 问,10 分钟)**:
1. 产品有没有 GUI?GUI 是不是主要形态?(是 → 倾向 GUI-first)
2. 裸跑 CLI 要不要独立登录?登录态和 GUI 通不通?(不通 → CLI 是"手"不是"脚")
3. CLI 的 headless/ACP 模式是不是产品的完整功能面?(缺 bundle/缺路由 → 说明 CLI 是裁剪版)
4. 产品有没有本地 Gateway/Daemon(监听端口、REST、SSE)?(有 → 优先驱动它)
5. 有没有官方文档明示 CLI 的定位?(acp.md/headless.md 是"手"还是"脚"?)

> **今天的教训**:workbuddy 自报"支持 `codebuddy --acp`"——字面全真,但没说是**裁剪版 bundle**(lite-wb),且凭证体系独立。自报信息要信一半,**判定清单走完再定路线**。

## 第 2 章 · 三种下行传输模板(适配器骨架)

适配器 = 一个**本机进程**:向上对 harnessd 说 ACP stdio,向下对厂商本体说话。harness-mesh/harnessd 零改动。

### 模板 A:CLI stdio(GUI-first 之外的大多数)

```
plugs.json → command: <harness CLI 全路径>, args: ["--acp"(+ --port 避让)]
harnessd 直接 spawn,stdio 即 ACP。无需适配器。
```
坑位备忘:CLI 内置端口撞车(加 `--port 5888`/`0`);env 要显式给全(见第 4 章)。

### 模板 B:GUI Gateway REST(workbuddy 走这条)

```python
# wb-gateway-adapter.py(~50-80 行,骨架)
# 向上:ACP stdio(initialize / session/new / session/prompt / session/update 通知)
# 向下:GUI Gateway REST(POST /api/runs 发起;轮询或 SSE 收事件→转 session/update)
# 凭证:复用 GUI 活登录态(密码从 GUI 配置/进程 env/用户一次性填报取,见下)
```

最小语义映射(第一版):
| ACP(向上) | Gateway(向下) |
|---|---|
| initialize | (空响应/健康检查) |
| session/new | 建 run(带 cwd/model) |
| session/prompt | 向 run 投 prompt |
| session/update(通知) | run 事件流(轮询/SSE)转译 |
| session/cancel | 取消 run |
| request_permission | 第二版(Gateway 有审批概念才做) |

### 模板 C:Daemon HTTP

同 B,把下行换成 daemon 的 RPC;若 daemon 原生说 ACP over HTTP,则适配器只需协议转制(HTTP 帧 ↔ stdio NDJSON)。

## 第 3 章 · 适配器契约(写任何适配器都遵守)

1. **向上只说 ACP stdio**:NDJSON、JSON-RPC 2.0、协议版本 1;方法面按需实现,但 `initialize/session_new/session_prompt` 必须有
2. **退出必须带死因**:适配器退出码非 0 时,stderr 尾部即死因——harnessd 的 `task.exit` 会把它回传主控(已实装),**别吞错误**
3. **凭证三选一,写进适配器配置**:复用本体(GUI/daemon 活登录态)> 读本体配置/进程 env > 用户一次性填报;**禁止要求新增独立登录**
4. **env 显式化**:适配器需要什么 env 在自己的配置里列全,不依赖继承(见第 4 章)
5. **无状态**:适配器实例不含跨任务状态;harnessd 每任务 spawn 一个,并发天然隔离
6. **可观测**:关键路径打 stderr(发起/收到/转译/退出),主控侧 task.exit 可见

## 第 4 章 · env 对齐纪律(今天第二条教训)

- workbuddy 的 bash 环境自带 `CODEBUDDY_FORCE_LITE_WB_BUNDLE=1`(会话注入),导致它的 `-p` 测试一直走通,**掩盖了裸环境的 MODULE_NOT_FOUND**
- **纪律:验证对端行为时,验证环境的 env 必须与 harnessd spawn 时的 env 显式对齐**——适配器需要的 env 全部写进 plugs.json 的 `env` 段,验证时也用同一份
- 反例警惕:"我这边跑通了"——先问"你的 env 和 spawn 时一样吗?"

## 第 5 章 · 排错手册(按形态)

| 现象 | 形态 | 第一嫌疑 |
|---|---|---|
| 任务秒 failed,error 含 MODULE_NOT_FOUND | CLI-first | bundle 裁剪/路径错——查安装包实际发了什么 |
| ACP connection closed,耗时 4-7s | 任意 | 执行体起来就退——要 stderr(部署带 task.exit 的 harnessd) |
| CLI 要独立登录/TUI 不退 | GUI-first | 形态误判——回第 1 章 |
| Gateway 401 | GUI-first | 凭证获取路径没通(第 3 章第 3 条) |
| 拨不通/超时 | 任意 | IP 漂移(tailnet),以 ctrl node list 为准 |
| health unknown | 任意 | 节点没打 tag(ACL 拒)或 harnessd 没起 |
